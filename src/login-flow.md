# Login & Routing Workflow (Ory Hydra + Workspace/Customer)

เอกสารสรุปขั้นตอนการจัดการระบบ Login และการตรวจสอบเส้นทาง (Routing) ของระบบ **fmp-id** โดยมีการใช้งานร่วมกับ **Ory Hydra** (OAuth2/OpenID Connect) และการแยกส่วนจัดการตาม **Workspace** และ **Customer**

---

## 1. การจัดการ Path และการตรวจสอบตัวตน (Authentication Check)
เมื่อมีการเรียกใช้งาน URL ต่างๆ ระบบจะดำเนินการตามลำดับดังนี้:

*   **Path `/` (Root):** ระบบจะทำการตรวจสอบการเข้าสู่ระบบ หากยังไม่ได้ Login จะทำการล้าง Cookie `customer` และ `workspace` ก่อนส่งไปหน้า Login
*   **Path `/ws` และ `/cs`:** ใช้สำหรับแยกส่วนการทำงาน (Segmentation) ระหว่าง **Workspace (ws)** และ **Customer (cs)**
*   **กระบวนการตรวจสอบ (Guard):** หากมีการเข้าถึงเส้นทางต่างๆ แล้วพบว่ายังไม่ได้ Login หรือไม่พบข้อมูลยืนยันตัวตน (โดยเฉพาะที่ Path `/`) ระบบจะ:
    1.  **Clear Cookies:** ล้างค่า `customer` และ `workspace` ออกจากเบราว์เซอร์
    2.  **Redirect:** ส่งผู้ใช้ไปยังหน้า `/login`
    3.  **Hydra Integration:** ส่ง `login_challenge` ไปยัง Ory Hydra เพื่อเริ่มกระบวนการ OAuth2/OIDC Flow

## 2. ขั้นตอนการ Login (`/login`)
เมื่อผู้ใช้เข้าสู่หน้า Login UI:

*   **ข้อมูลเบื้องต้น:** ระบบจะทำการดึงข้อมูล Client จาก Hydra เพื่อเตรียมความพร้อมของฟอร์ม
*   **Interface:** เรนเดอร์หน้าจอ Login ให้ผู้ใช้กรอก Username และ Password
*   **เงื่อนไขการเข้าถึง (Authorization):** มีการตรวจสอบความสัมพันธ์ระหว่างผู้ใช้กับ **Workspace (ws)** และ **Customer (cs)** โดยเฉพาะการตรวจสอบสิทธิ์ว่ามี Role เป็น `admin` หรือไม่ ตามที่ระบุไว้ในเงื่อนไขทางธุรกิจ

## 3. กระบวนการ Callback และการรับ Token (`/callback`)
หลังจากผู้ใช้ผ่านการพิสูจน์ตัวตนจากหน้า Login ระบบจะถูกส่งกลับมายังจุดรับข้อมูล (Callback):

1.  **ดึงข้อมูล Authorization Code:** รับค่า `oc` (Authorization Code) จาก Query String ที่ Hydra ส่งกลับมา
2.  **แลก Token (Token Exchange):** นำค่า `oc` ส่งกลับไปที่ Ory Hydra ผ่าน Server-side request เพื่อแลกเป็น:
    *   **Access Token:** สำหรับเรียกใช้งาน API
    *   **Refresh Token:** สำหรับต่ออายุ Session
3.  **บันทึกสถานะ (Session Persistence):** นำข้อมูลที่จำเป็น (เช่น `ssid` หรือ Session ID ที่ได้จาก Token) มาบันทึกลงใน **Cookie** เพื่อใช้ยืนยันตัวตนในการร้องขอครั้งถัดไป
4.  **เสร็จสิ้น:** ทำการ Redirect ผู้ใช้กลับไปยัง Frontend หลักตามที่กำหนดไว้ในสถานะเริ่มต้น

## 4. การจัดการกรณีเกิดข้อผิดพลาด (Error Handling)
ระบบมีการเตรียมพร้อมสำหรับกรณีที่ไม่สามารถหาข้อมูลที่จำเป็นได้ เพื่อป้องกันการเข้าถึงที่ผิดพลาด:

*   **ไม่พบ Workspace:** ระบบจะไม่สามารถระบุขอบเขตข้อมูลได้
*   **ไม่พบ Customer:** ระบบจะไม่สามารถระบุตัวตนผู้ใช้งานได้
*   **การตอบสนอง:** ในกรณีเหล่านี้ ระบบจะ Redirect ผู้ใช้กลับไปยังหน้าเริ่มต้น หรือแสดงหน้า Error (เช่น 404 Not Found หรือ 401 Unauthorized) เพื่อความปลอดภัยและความชัดเจนของผู้ใช้งาน
